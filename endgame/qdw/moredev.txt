# StallSpy Company Substrate — Implementation Brief

You have local access to three repositories:

* `StallSpy` — the domain/product repository you are implementing.
* `private-lab` — local name for `prx0r/qdw-workbench`; this is the canonical company kernel.
* `finalbuilds` — `prx0r/finalbuilds2`; treat primarily as a donor/reference implementation.

## 0. Objective

We are not building a standalone Etsy automation app.

We are building the first real economic environment operated by a general agent-company substrate.

The architecture must support this loop:

```text
OBSERVE WORLD
    ↓
ASSESS STATE
    ↓
DETECT PROBLEMS / OPPORTUNITIES
    ↓
FORM HYPOTHESES
    ↓
DESIGN CONTROLLED INTERVENTIONS
    ↓
ALLOCATE MONEY / TOKENS / HUMAN ATTENTION
    ↓
EXECUTE THROUGH TYPED CAPABILITIES
    ↓
CAPTURE TRAJECTORY + RECEIPT
    ↓
OBSERVE DELAYED ECONOMIC OUTCOMES
    ↓
INDEPENDENT / COLD REVIEW
    ↓
ATTRIBUTE RESULTS
    ↓
LEARN / PROMOTE / REJECT
    ↓
NEXT COMPANY STATE
```

Etsy/Dogcasso is the first world.

The same substrate must later be able to run security work, Bittensor, software gigs, Metaculus, other storefronts, marketing teams, etc.

Therefore:

> Domain-specific facts belong in StallSpy. Universal company machinery belongs in private-lab.

Do not create a second ledger, second generic experiment framework, second worker registry, second memory truth store, or second orchestration ontology inside StallSpy.

If swapping PydanticAI for another runtime destroys historical comparability, the architecture is wrong.

If an Etsy API response becomes the application's canonical domain object, the architecture is wrong.

# 4. Harden private-lab before extending it

The kernel is close but has several correctness issues that must be fixed first.

## 4.1 Make ledger append transactional

Current ledger flow reads `previous_event_hash` separately from the INSERT.

That can fork the hash chain under concurrent writers.

Refactor append into one transaction:

```text
BEGIN IMMEDIATE

SELECT final event hash

construct next event

INSERT next event

COMMIT
```

The read of the previous hash and insertion must use the same connection and transaction.

Add a concurrent-write test with multiple writers.

Acceptance criterion:

```text
100+ concurrent appends
→ all succeed or fail explicitly
→ verify_chain().valid == true
→ no two canonical events claim the same previous hash
```

unless one is explicitly the genesis event.

## 4.2 Fix event ID semantics

The code/documentation currently describes IDs as UUIDv7/time ordered while generation does not actually provide a proper UUIDv7.

Either:

* implement real UUIDv7; or
* use another explicitly time-sortable ID contract;

but do not claim UUIDv7 unless it is UUIDv7.

Preserve backward compatibility with existing IDs.

## 4.3 Make Hydra projection pure

Projection MUST NOT create new canonical events.

A projector:

```text
Ledger → Hydra
```

must never become:

```text
Ledger → Hydra → new Ledger events
```

Move any `run.outcome_recorded` event creation out of projector code and into the evaluator/controller that actually knows the event occurred.

Add this invariant:

```text
count_before = ledger.count_events()
projector.rebuild()
count_after = ledger.count_events()

assert count_before == count_after
```

Run rebuild twice.

Graph output must be equivalent on both runs.

## 4.4 Make all state changes ledger-first

Audit `LabController`.

Do not allow business-significant facts to be written directly into Hydra.

Required pattern:

```text
domain action
    ↓
ledger.append_event(...)
    ↓
projector
    ↓
Hydra
```

Never:

```text
domain action → Hydra only
```

Inject one shared service container into controller/executors:

```text
LabServices
├── ledger
├── artifacts
├── projector
├── worker_registry
├── evaluator
├── budget
├── policy
├── executor
└── git
```

Remove creation of random local `Ledger()` or `ArtifactStore()` objects inside execution paths where a canonical shared service should be used.

## 4.5 Preserve published contract compatibility

The current contracts explicitly state that published contracts should not simply be mutated.

Respect this.

There are Letta-specific remnants such as:

```text
Worker.letta_agent_id
TrajectoryRef.format = "letta-trajectory"
```

Do NOT destructively rename these fields.

Introduce neutral v2 contracts or backward-compatible adapters, for example:

```text
WorkerIdentityV2
    runtime_agent_id
    runtime_type

TrajectoryRefV2
    format = "agent-trajectory/v1"
```

Old receipts must remain loadable.

Do not make this a giant god-function.

Model it as a state machine.

Proposed phases:

```text
COLLECT
    gather first-party world state

ASSESS
    create independent state assessments

DIAGNOSE
    generate Problems

HYPOTHESIZE
    generate/research Hypotheses

ALLOCATE
    assign budget, workers, models, human attention

EXECUTE
    issue WorkOrders and interventions

OBSERVE
    capture immediate/delayed outcomes

REVIEW
    blind/cold review

LEARN
    create Findings, proposals, policy/worker candidates

CLOSE
    seal CompanyDay
```

Each transition emits ledger evidence.

If using `pydantic-graph`, this is an appropriate place for it.

The graph is runtime orchestration.

The ledger remains truth.

# 33. First end-to-end vertical slice

5. Detect one Problem.
6. Produce one ResearchBundle.
7. Produce one Hypothesis.
8. Design one WorldExperiment.
9. Create one WorkOrder.
10. Compile one proposed listing change.
11. Run policy evaluation.
12. In SHADOW/REPLAY, produce an `InterventionProposed` without external mutation.
13. Generate complete RunReceipt.
14. Feed a fixture delayed outcome.
15. Run ColdReview using an enforced information boundary.
16. Evaluate experiment.
17. Produce Finding.
18. Project everything into Hydra.
19. Delete/rebuild Hydra.
20. Verify the reconstructed graph is equivalent.

This proves the architecture.

# 38. AGENTS.md

Create a concise `AGENTS.md` in StallSpy with these axioms:

```text
1. private-lab owns canonical history.
2. StallSpy owns Etsy/Dogcasso domain semantics.
3. Hydra and memory stores are derived.
4. Every external side effect is typed, policy-gated and receipted.
5. No agent receives unrestricted credentials.
6. External research is evidence with provenance, not truth.
7. Every meaningful decision should be attributable to exact inputs and versions.
8. Blind review means enforced information separation.
9. Controlled experiments are distinct from observational analytics.
10. Product/template definitions are immutable versions; performance is separate observation data.
11. Do not optimize metrics without defining the economic objective and guardrails.
12. Prefer one complete measured loop over ten partially built subsystems.
```

Add:

> Before introducing a new framework/database/orchestrator, prove it supplies a capability not already owned by private-lab.

# 42. Definition of success

Do not judge success by lines of code.

The pass succeeds when this command/workflow is possible conceptually:

```text
stallspy company-day run --mode replay --fixture demo-shop
```

and it produces a verifiable chain like:

```text
CompanyDay
→ StateSnapshot
→ independent ActorAssessment
→ Problem
→ ResearchBundle
→ Hypothesis
→ WorldExperiment
→ WorkOrder
→ InterventionProposed
→ RunReceipt
→ OutcomeObservation
→ ColdReview
→ ExperimentResult
→ Finding
```

with:

```text
all artifacts content-addressed
all canonical facts in ledger
all graph state rebuildable
all agent/model/tool versions attributable
all costs attributable
all information boundaries recorded
all actions policy checked
all external effects idempotent
```

Then run:

```text
delete Hydra
rebuild Hydra
verify lineage
```

and obtain the same company history.

That is Checkpoint 1.

Checkpoint 2 is the same loop against a real Etsy shop in SHADOW mode.

Checkpoint 3 is one approved, reversible LIVE intervention whose later economic outcome is attached to the exact hypothesis, experiment, worker, model, context, cost and human decisions that produced it.

Do not move on to broad autonomy until Checkpoint 3 is real.

# 43. Architectural end state

The intended system is:

```text
                         PRIVATE-LAB
                    Canonical Company Kernel
                              │
          ┌───────────────────┼────────────────────┐
          │                   │                    │
        Truth              Cognition            Learning
          │                   │                    │
       Ledger             PydanticAI         Experiments
       Artifacts           Workers            Attribution
       Git                 Context            Reconciliation
       Receipts            Capabilities       Allocation
          │                   │                    │
          └───────────────────┼────────────────────┘
                              │
                         STALLSPY WORLD
                              │
             ┌────────────────┼─────────────────┐
             │                │                 │
          Etsy API         Research          Dogcasso
          Webhooks         EverBee           Templates
          Orders           Signals           Renders
          Reviews                            Fulfillment
             │                │                 │
             └────────────────┼─────────────────┘
                              │
                      ECONOMIC OUTCOMES
                              │
                              ▼
                         PRIVATE-LAB
```

FinalBuilds becomes both:

1. a source of machinery that is generalized into private-lab; and
2. later, a product-building/intelligence module running on top of the same substrate.

The core rule is:

> StallSpy should teach private-lab how to operate a real business without turning private-lab into Etsy software.

Build toward that.
